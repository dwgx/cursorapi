## S1 并发 SSE 流(50/100/200)+ 日志风暴

做法:开 N 个消费中的 `/admin/logs` 连接(带 session cookie),稳定后灌 3000 条 1KB 日志(经 monitor 注入 `logger.mjs` 真实 emit 路径),记录每连接收到的 data 帧数(预期 3000 风暴 + 50 回放 = 3050)。

| 连接数 | 注入耗时 | RSS 前后 (MB) | 帧送达 min/avg/max | 送达率 | 丢帧 |
|---|---|---|---|---|---|
| 50 | 658ms | 56.0 → **249.8** | 964/965/965 | 31.6% | 68.4% |
| 100 | 1981ms | 46.8 → **117.1** | 1006/1007/1007 | 33.0% | 67.0% |
| 200 | 737ms | 51.2 → **491.5** | 1006/1007/1007 | 33.0% | 67.0% |

**丢帧是否生效:是,且按设计工作。** 证据链:3000×1KB=3MB 写入,cap 1MB → 理论上保留 33%;实测 31.6-33%,完全吻合 `app.mjs:283-287` 的 `res.writableLength > SSE_BUFFER_CAP` 判定。日志注入是**同步循环**(`logger.mjs:106-115` emit 无 await),风暴期间事件循环完全阻塞,消费客户端也读不到,全部帧先堆进 writableLength,超 1MB 即丢。

**瓶颈定位:**
- `logger.mjs:44-46` `append()` 广播时,**每帧字符串在 cap 判定之前就已构造**:subscriber 回调 `(e) => writeFrame(\`data: ${JSON.stringify(e)}\n\n\`)`(`app.mjs:291`)在调用 writeFrame 前求值模板串。风暴下 200 连接 × 3000 帧 × ~1.2KB ≈ 720MB 的瞬时字符串构造,cap 只能拦住 res.write,拦不住构造——这就是 200 连接 RSS 峰值 491MB 的来源(第一次运行同样吻合:188/204/222MB)。
- 注入速率 815/556/1053 条/s:同步广播成本随连接数增长(100 连接最慢 1981ms,是构造量最大的档)。

**内存曲线**:每档灌后 RSS 回落(100 档 46.8MB 基线是 GC 已回收),峰值即瞬时构造压力,非稳态泄漏。S5 结束后最终回落到 29.3MB,证明全部可回收。

## S2 并发账号操作(20/70)

做法:空池启动。并发 POST `/admin/accounts`(mock key,`vetCandidate` 走真实校验路径含 `Cursor.me`)、`/admin/accounts/{id}/disabled`、`/probe`。每轮后校验 accounts 文件:JSON 可解析 + 条目数精确 + key 无重复。

| 操作 | 并发 | 墙钟 | 每请求 p50/p95 | 失败 | 文件校验 |
|---|---|---|---|---|---|
| 批量添加 | 20 | 82ms | 46/79ms | 0 | 20 条,合法,唯一 |
| 批量添加 | 50 | 195ms | 100/184ms | 0 | 70 条,合法,唯一 |
| disable | 20 | 72ms | 41/71ms | 0 | 70 条不变 |
| disable | 70(满池) | 222ms | 107/210ms | 0 | 70 条不变 |
| enable | 70(满池) | 236ms | 123/221ms | 0 | 70 条不变 |
| probe | 20 | 5ms | 4/5ms | 0 | - |
| probe | 70(满池) | 10ms | 7/8ms | 0 | - |
| 混合 20d+20e+30p | 70 | 162ms | 131/160ms | 0 | 70 条不变 |

注:需求是 20/50 两档,高并发档直接用了满池 70 个 id(≥50,覆盖)。

**写队列串行(文件不损坏):确认。** 证据:并发添加后文件精确 20/70 条、无重复 key、每轮校验 JSON 合法——`keys.mjs:1147-1152` 的 `enqueueFileWrite` 无 lost update。串行成本:添加 50 个 195ms(每次 = `vetCandidate`(mock 零延迟) + `readStore` + `writeStore` 含 **fsync**(`keys.mjs:722-742` tmp+fsync+rename) + `loadAccounts` 全池重扫),即 fsync + 重扫主导。真实环境 `Cursor.me` 网络校验是主要成本,串行化是正确取舍。

**probe 无锁并发(5-10ms)**:`probeOne`/`probe`(`keys.mjs:1330-1410`)只读 + 改内存态,无共享写文件,并发安全无瓶颈。

做法:50 个 worker 持续 POST `/v1/chat/completions`(stream:true,mock 流一次文本+usage 即结束),50 个 worker 持续 GET `/admin/status`,60 秒。15s 窗口记录吞吐。

| 指标 | 数据面(流式) | /admin/status |
|---|---|---|
| 请求数 | 71114 | 71555 |
| 吞吐 | 1184/s | 1192/s |
| p50 / p95 / p99 | 31 / 106 / 175ms | 31 / 107 / 172ms |
| max / mean | 877 / 42ms | 772 / 42ms |
| 失败 | 0 | 0 |

**退化曲线**(15s 窗口完成的请求数):

| 窗口 | 数据面 | status | 环比 |
|---|---|---|---|
| 0-15s | 25745 (1716/s) | 26009 (1734/s) | - |

| 30-45s | 15075 (1005/s) | 15085 (1006/s) | -21% |

**定位:** 单线程事件循环饱和下的自然退化,无代码缺陷证据(0 失败、双面同比例降、无异常句柄增长)。每请求固定开销 = 流式 SseWriter 逐帧 JSON + keep-alive 连接复用;60s 后 GC 压力上升(见 S4 起始 RSS 221.8MB 未回收)。p99 175ms 说明尾部有 GC 停顿。对比 bench 历史:流式 @20 单压 4-5k/s,混合 50+50 下 1.2k/s 量级一致,退化来自资源竞争而非代码。

## S4 慢客户端(不消费 + 500ms 慢读)

做法:5 个 SSE 连接**完全不读 body** + 1 个 500ms 间隔慢读连接,灌 20000×1KB 日志,1s 间隔采样 RSS。

- 注入 20000 条仅 299ms(同步广播短路径)。
- 慢读连接收到 **419 帧**(预期 20050,含 50 回放)→ **送达率 2%**,丢帧生效:`app.mjs:283-287` cap 判定,`writableLength` 顶到 1MB 即丢。
- **内存有界**:灌入后峰值 239.3MB vs 灌入前 GC 基线 ~54MB → 增量 ~185MB,由 6 连接 × 24MB 同步构造 + ~1MB×6 写缓冲 + ring 构成;RSS 曲线 `[161.9, 133.3, 53.9, 56.5, 239.3, 239.3, 239.3]`(前 3 点是 S3 残留 GC 回落,后 3 点为封顶稳态,不再增长)。
- 无连接中断、无服务器故障。**背压工作正常**,且丢帧是逐连接独立的。

注:185MB 增量中大部分是「帧字符串先构造后判 cap」的瞬态(见 S1 定位),稳态常驻仅 ~6MB 写缓冲 + ring 1MB。

## S5 连接风暴(100/s × 30s)

做法:驱动每 100ms 开 10 个 SSE 连接,20-50ms 后关闭,同时每秒灌 10 条日志,持续 30s(实际 2940 次,84/s,0 失败——driver 侧调度粒度所致,量级达标)。

| 指标 | 前 | 后 |
|---|---|---|
| RSS | 233.4 MB | 51.0 MB |
| lsof(fd) | 120 | 110(开合期间)+ 最终 **15** |
| 句柄 | Server 1, Socket 105 | Server 1, Socket 95(最终回收) |

**无泄漏。** Socket 105 是 undici keep-alive 池的空闲连接(服务端 `keepAliveTimeout=75s`,`app.mjs:438`),S6 的 70s 等待期内全部被服务端超时回收,最终 lsof 15 与 P0 基线(17)持平。SSE 关闭路径(`app.mjs:292-295` clearInterval + unsub)无定时器残留——handles 里无 Timeout/Immediate 增长。

## S6 热更新并发(60s 内多次 /admin/update/check)

做法:fetch-hook 替换全局 fetch 并逐次落盘计数(`pressure2/fetch-hook.mjs`);50 并发 → +3s 后 50 并发(60s TTL 内)→ +61s 单发(TTL 过期)。

| 批次 | 墙钟 | p50/p95 | fetch 调用数 | 说明 |
|---|---|---|---|---|
| 50 并发(0s) | 67ms | 66/66ms | **1** | 共享 inFlight,一次上游 |
| 50 并发(+3s) | 21ms | 16/18ms | **1** | cache hit,p50 降 76% |
| 1 次(+61s) | 132ms | 132ms | **2** | TTL 过期,重新上游 |

**ttlCache 完全生效:** `app.mjs:212-213` + `http-helpers.mjs:88-106` 的 inFlight 共享 + 60s 缓存,50 并发同刻只产生 1 次 GitHub 请求;命中时 p50 66→16ms。fetch 计数与预期严格一致(1/1/2)。

## 优化建议(按价值排序)

1. **cap 判定前移,别先构造后丢弃(高价值)**。`app.mjs:291` 的订阅回调在进入 `writeFrame` 前就构造了整帧字符串,风暴下 200 连接瞬时多分配 ~700MB(实测 RSS 491MB 的主因)。改为:subscriber 层维护 per-connection pending 字节计数,超 cap 直接跳过序列化(或把序列化移进 `writeFrame` 内、判定在前)。预计 S1 峰值内存降 ~60-70%,S4 增量同理。改动小,收益大。
2. **SSE_BUFFER_CAP 按连接计费的取舍(中价值)**。1MB/连接 × 200 连接 = 200MB 理论上限(`app.mjs:266`)。对面板类订阅者 256KB 已足够(50 帧回放 ≈ 60KB);若担心风暴丢帧观感,可在 replay 后按消费者实际吞吐动态收窄。配合建议 1 一并做。
3. **慢客户端旁路(中价值)**。S4 显示慢客户端送达率仅 2%,订阅还在白做序列化。可在多次连续 drop 后对该订阅者降级为「只收心跳 + 满阈值时重连拉 replay」,省掉风暴中的无效构造。属增强,非缺陷修复。
4. **批量账号导入入口(低价值)**。单账号添加串行 fsync(195ms/50)是正确性设计,批量接口 `addAccounts`/`batchOps` 已存在且更高效(验证一批、写一次)。面板上引导批量粘贴即可,服务端无需改动。
5. **S3 尾段 GC 抖动(低价值)**。p99 175ms 与 15s 窗口退化由单线程事件循环 + GC 饱和导致,非代码缺陷。若要多扛并发,方向是拆分进程或调 `--max-old-space-size`/`--optimize-for-size`;当前 8GB 单机 1200 req/s 量级下不建议为此动架构。
